> 작성일: 2026-05-14  
> 범위: Supabase Auth 기반 Google, Kakao OAuth 로그인 추가 — 기존 사용자/선수/팀 플로우 연결

## 1. 기술 스택 요약

| 항목 | 버전 / 패키지 |
|------|--------------|
| Framework | Next.js 15 (App Router, Server Components) |
| React | 19.x |
| TypeScript | 5.x strict |
| Auth | `@supabase/ssr` 0.8.0 + `@supabase/supabase-js` 2.95.3 |
| 세션 관리 | 쿠키 기반 SSR 패턴 (`createServerClient`) |
| Styling | Tailwind CSS 4 |
| 배포 | Vercel (환경: production / preview / development) |

**핵심 아키텍처 특징**

- 모든 보호 페이지는 **Server Component** + `getUserWithRole()` 직접 호출 방식
- `middleware.ts` **없음** — 세션 인증은 전적으로 페이지 레벨에서 처리
- `createSupabaseServerClient`가 `React cache()`로 래핑 → 요청당 1회만 Supabase 연결
- DB 트리거 `handle_new_user()`가 `auth.users` INSERT 시 `profiles` 행을 자동 생성

## 3. 현재 구현 상태

### 3-1. 인증 흐름 (이메일/비밀번호 기준 현재 동작)

```
[회원가입]
signup/Form.tsx
  → signUpWithPassword() 서버 액션
    → supabase.auth.signUp({ email, password, options.emailRedirectTo })
    → emailRedirectTo = /auth/callback?next=/onboarding/completion?step=signup
  → "이메일 확인 안내" 표시 OR 즉시 리다이렉트
  → 이메일 링크 클릭 → /auth/callback?code=xxx&next=...
    → exchangeCodeForSession(code) → 세션 생성
    → next 파라미터 경로로 리다이렉트 → /onboarding/completion?step=signup

[로그인]
login/Form.tsx
  → signInWithPassword() 서버 액션
    → supabase.auth.signInWithPassword()
    → getCurrentUserRole() 호출
    → organizer/manager → /admin
    → player → /dashboard
    → user → /

[로그아웃]
logoutAction()
  → supabase.auth.signOut()
  → redirect("/")
```

### 3-2. DB 사용자 생성 책임

- **DB 트리거** `handle_new_user()` (migration `0002_profiles_roles.sql`)가 `auth.users`에 새 행 INSERT 시 `profiles` 행을 자동 생성
- `profiles.role` 기본값: `'user'` (migration `0215_role_add_user.sql`)
- **결론**: OAuth 로그인 시에도 트리거가 자동 실행 → 별도 서버 액션 없이 profiles 행 생성됨

### 3-3. 약관 동의 (현재 이메일 가입에만 존재)

- `signUpWithPassword()` 액션 내 `recordTermsConsentBatch()` 호출
- `user_terms_consents` 테이블 기록
- OAuth 흐름에서는 별도 처리 필요 (콜백 이후 동의 단계 or 최초 진입 시 동의 수집)

## 4. 재사용 가능한 패턴

### 4-1. OAuth 콜백 처리 — `/app/auth/callback/route.ts` 재사용 가능

```typescript
// 현재 구현 (이메일 확인 링크용)
const { error } = await supabase.auth.exchangeCodeForSession(code);
if (!code) → redirect("/login?error=missing_code")
if (error) → redirect("/login?error=...")
redirect(next ?? "/dashboard")
```

**Supabase OAuth는 같은 PKCE 코드 교환 방식**을 사용하므로 이 콜백 라우트를 그대로 재사용할 수 있다.  
단, OAuth 신규 사용자와 기존 사용자를 구분해 `next` 경로를 결정하는 로직 추가가 필요하다.

### 4-2. `getUserWithRole()` — 역할 기반 분기 그대로 활용

로그인 완료 후 역할 확인 및 리다이렉트 로직은 이미 `login/actions.ts`에 완성되어 있다.  
OAuth 로그인 후에도 동일한 분기 (`organizer/manager → /admin`, `player → /dashboard`, `user → /`) 적용 가능.

### 4-3. Server Action 에러 반환 패턴

```typescript
type ActionResult = { ok: true } | { ok: false; error: string };
```
OAuth 트리거 서버 액션도 이 패턴을 따른다.

### 4-4. 에러 메시지 번역 맵 패턴

`login/actions.ts`의 `translateAuthError()` 함수처럼 OAuth 에러 코드 → 한국어 메시지 맵 추가 가능.

### 4-5. Identity Adapter 인터페이스 패턴

`src/lib/identity/adapter.ts`의 `IdentityVerificationAdapter` 인터페이스처럼,  
OAuth provider 설정도 adapter 패턴으로 추상화 가능 (선택적).

-- profiles 테이블 (핵심 컬럼)

| OAuth provider 정보 저장 | 선택적 | `auth.users.raw_app_meta_data`에 이미 provider, provider_id 저장됨 |
| `profiles.avatar_url` 컬럼 추가 | 선택적 | Google/Kakao 프로필 이미지 저장 원하면 추가 |

| 약관 동의 (user_terms_consents) | 별도 처리 필요 | OAuth 콜백 이후 약관 동의 수집 흐름 추가 |

**결론: 신규 마이그레이션 없이 기존 구조로 OAuth 사용자 수용 가능.**

### 5-5. 권한 정책 (RLS)

**현재 RLS 정책 분석:**

```sql
-- profiles SELECT 정책
CREATE POLICY "profiles_select_own_or_organizer"
  ON public.profiles FOR SELECT
  USING (id = auth.uid() OR public.is_organizer());

-- profiles UPDATE 정책
CREATE POLICY "profiles_update_own"
  ON public.profiles FOR UPDATE
  USING (id = auth.uid()) WITH CHECK (id = auth.uid());
```

**OAuth 사용자 호환성:**

- 모든 RLS 정책이 `auth.uid()` 기반 → Supabase OAuth 세션도 `auth.uid()` 정상 반환
- `is_organizer()`, `is_player()`, `is_team_member_for_team()` 등 SECURITY DEFINER 함수도 `auth.uid()` 조회 → 영향 없음
- `teams`, `team_members`, `applications` RLS 정책 — OAuth 사용자가 팀 생성 시 `created_by = auth.uid()` 조건 정상 동작

**RLS 변경 불필요.** OAuth와 이메일/비밀번호 인증 방식은 Supabase 세션 레벨에서 동일하게 취급됨.

## 7. 구현 시 주의사항

### 7-1. OAuth 신규 유저 vs 기존 유저 구분 — 콜백 리다이렉트 분기

현재 `/app/auth/callback/route.ts`는 `next` 파라미터를 그대로 리다이렉트한다.  
OAuth 로그인의 경우 신규/기존 사용자 모두 같은 콜백 URL을 거치는데, 이 두 케이스의 `next` 경로가 다르다:

- **신규 사용자** → `/onboarding/completion?step=signup`
- **기존 player** → `/dashboard`
- **기존 organizer/manager** → `/admin`

**해결 방법 (권장)**:  
콜백 라우트에서 `exchangeCodeForSession()` 후 `getUserWithRole()`을 호출해 역할을 확인하고 분기 처리.  
또는 `supabase.auth.getUser()`의 응답에서 `user.created_at`과 현재 시각을 비교해 신규 유저 판단 (5초 이내 생성이면 신규).

```typescript
// 콜백 route.ts 개선 예시
const { data: { user } } = await supabase.auth.getUser();
const isNewUser = user && (Date.now() - new Date(user.created_at).getTime()) < 10_000;
if (isNewUser) redirect("/onboarding/completion?step=signup");
// 기존 유저 → 역할 기반 분기
```

### 7-2. Kakao 이메일 미제공 문제

Kakao OAuth는 사용자가 이메일 제공에 동의하지 않으면 `auth.users.email`이 `null`이 된다.

**현재 코드에서 email 참조 위치 점검 필요:**

- `src/lib/auth/roles.ts`의 `AuthUser.email: string | null | undefined` → **이미 null 허용**
- `app/(app)/layout.tsx` 사이드바 사용자 이메일 표시 → null 처리 필요 (예: "카카오 사용자" 표시)
- `lib/api/auth.ts`의 `signInWithPassword()`, `signUpWithPassword()` → 이메일 필수 입력 방식이므로 OAuth와 무관
- `user_profiles` 뷰: `JOIN auth.users u ON u.id = p.id` — email null 가능성 있지만 뷰 자체는 문제 없음

**결론**: 이메일 null 케이스를 UI에서 graceful하게 처리하면 된다. DB 스키마나 RLS 변경 불필요.

### 7-3. 약관 동의 처리

현재 이메일 회원가입 시 `recordTermsConsentBatch()`가 `signUpWithPassword()` 액션 내에서 호출된다.  
OAuth는 서버 액션을 거치지 않으므로 약관 동의 수집 지점이 없다.

**선택지:**

| 방식 | 장점 | 단점 |
|------|------|------|
| A. OAuth 콜백 후 약관 동의 페이지 삽입 | 기존 이메일 가입과 동일한 보호 수준 | UX 단계 증가 |
| B. 최초 온보딩 진입 시 약관 동의 팝업 | UX 흐름 자연스러움 | 구현 복잡도 증가 |
| C. Google/Kakao는 서비스 약관 동의 간주 처리 | 구현 최소화 | 법적 리스크 (개인정보처리방침 등) |

**권장**: A안 (OAuth 콜백 → 약관 동의 페이지 → 온보딩). 법적 안전성이 가장 높다.

### 7-4. `redirectTo` URL 구성 — 배포 환경별 처리

현재 `signUpWithPassword()` 액션에서 `redirectTo` URL 조립 방식:

```typescript
const siteUrl =
  process.env.NEXT_PUBLIC_SITE_URL ??
  (process.env.VERCEL_URL ? `https://${process.env.VERCEL_URL}` : "http://localhost:3000");
const emailRedirectTo = `${siteUrl}/auth/callback?next=...`;
```

OAuth `signInWithOAuth()`의 `redirectTo`도 **동일한 패턴**을 따라야 한다.  
Supabase Dashboard에서 Redirect URLs에 프로덕션/프리뷰 도메인을 사전 등록해야 한다.

### 7-5. `supabase.auth.signInWithOAuth()` 호출 위치

이 함수는 **브라우저에서 호출**해야 한다 (서버 액션에서는 브라우저 리다이렉트 불가).  
따라서 `OAuthButtons.tsx`는 `"use client"` 컴포넌트여야 하고, `createSupabaseBrowserClient()`를 사용해야 한다.

```typescript
// OAuthButtons.tsx (Client Component)
"use client";
import { createSupabaseBrowserClient } from "@/src/lib/supabase/client";

async function handleOAuthLogin(provider: "google" | "kakao") {
  const supabase = createSupabaseBrowserClient();
  const { error } = await supabase.auth.signInWithOAuth({
    provider,
    options: {
      redirectTo: `${window.location.origin}/auth/callback?next=/onboarding/completion?step=signup`,
      // 기존 유저의 경우 콜백 내에서 역할 확인 후 재분기
    },
  });
  if (error) { /* 에러 처리 */ }
}
```

### 7-6. Supabase Dashboard 설정 (코드 외 작업)

다음 설정이 코드 구현 전에 완료되어야 한다:

1. **Authentication > Providers > Google** 활성화 + Client ID / Secret 입력
2. **Authentication > Providers > Kakao** 활성화 + Client ID / Secret 입력
3. **Authentication > URL Configuration > Redirect URLs**에 아래 URL 추가:
   - `http://localhost:3000/auth/callback`
   - `https://<production-domain>/auth/callback`
   - `https://<preview-domain>/auth/callback`
4. Kakao Developer Console에서 리다이렉트 URL 추가 필요

### 7-7. 기존 이메일 가입자와의 계정 연동 문제

동일 이메일로 이메일/비밀번호로 이미 가입한 사용자가 Google OAuth 로그인 시도 시:

- Supabase 기본 동작: **에러** 반환 (`User already registered` 또는 계정 연결 오류)
- 현재 프로젝트는 계정 연결/통합 기능이 **이번 구현 범위 제외**

대응: 콜백 에러 핸들링에 해당 케이스 포함, 에러 메시지로 안내 ("동일 이메일로 이미 가입된 계정이 있습니다. 이메일 로그인을 이용하세요.")

### 7-8. 현재 보호 페이지 가드 패턴과의 충돌 없음 확인

`app/(app)/dashboard/page.tsx` 등 보호 페이지는 `getUserWithRole()` 결과의 `status === "unauthenticated"` → `/login` 리다이렉트.  
OAuth 세션도 `supabase.auth.getUser()`로 정상 반환 → 기존 가드 동일하게 동작.  
**충돌 없음.**

### 7-9. 모바일 OAuth UX

- 모바일 브라우저에서 `signInWithOAuth()` 호출 시 새 탭 또는 인앱 브라우저로 provider 페이지 열림
- iOS Safari, Android Chrome 모두 OAuth Redirect 방식 지원
- Supabase 기본 동작이 `redirect` 방식이므로 별도 처리 불필요
- 단, 카카오는 카카오 앱 설치 여부에 따라 앱 전환이 발생할 수 있음 — 사용자 안내 문구 권장

## 9. 결론

### 핵심 발견 사항

1. **콜백 라우트가 이미 OAuth 호환** — `/app/auth/callback/route.ts`는 `exchangeCodeForSession(code)`를 사용하므로 OAuth PKCE 코드 교환도 그대로 처리 가능. 신규/기존 사용자 분기 로직만 추가하면 된다.

2. **DB 트리거로 사용자 생성 자동화** — `handle_new_user()` 트리거가 OAuth 신규 사용자의 `profiles` 행을 자동 생성하고 `role='user'`를 부여. 별도 서버 액션이나 마이그레이션 불필요.

3. **RLS 호환성 완전** — 모든 RLS 정책이 `auth.uid()` 기반이므로 OAuth 세션과 완전히 호환.

4. **마이그레이션 불필요** — 현재 DB 스키마로 OAuth 사용자 수용 가능. `profiles.email` 컬럼 없음 → Kakao 무이메일 제약 없음.

5. **구현 복잡도 낮음** — 코드 변경 범위가 명확하다: (1) 콜백 라우트 분기 추가, (2) OAuth 버튼 컴포넌트 신규 생성, (3) 로그인/회원가입 폼에 버튼 추가. 기존 아키텍처 변경 없음.

### 주요 리스크

| 리스크 | 수준 | 대응 |
|--------|------|------|
| Kakao 무이메일 UI 처리 누락 | 중 | email null 케이스 UI 방어 처리 |
| 기존 이메일 가입자 계정 충돌 | 중 | 에러 메시지로 안내, 계정 연동은 범위 외 |
| 약관 동의 누락 | 중~높음 | OAuth 콜백 후 약관 동의 단계 추가 필요 |
| Supabase Redirect URL 미등록 | 높음 | Phase 1에서 선행 처리 필수 |
| 신규/기존 유저 구분 오류 | 낮음 | `created_at` 기반 10초 이내 판단으로 충분 |
