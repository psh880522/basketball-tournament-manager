### STEP 2. 대회 상세

**현재**: `app/(app)/tournament/[id]/page.tsx` — 단일 컬럼 레이아웃, 대회 정보 + division 목록 + 신청 CTA 버튼

**구현된 것:**
- 대회 이름, 날짜, 장소, 상태 뱃지 표시
- division별 entry_fee, capacity 일부 표시
- 내 신청 상태 뱃지 (applicationStatusMap)
- "신청하기" / "신청 현황 보기" CTA 분기

**없는 것 (미구현):**
- 대회 포스터 이미지 표시 (poster_url 컬럼 있으나 상세에서 미표시 확인 필요)
- 대회 설명/규칙 텍스트 (tournaments 테이블에 description 필드 없음)
- 운영 방식(조별리그+토너먼트 등) 명시
- 로스터 수정 마감일 표시 (현재는 start_date = 마감, 별도 표시 없음)
- 각 division의 현재 신청 수 / 정원 실시간 표시

**목표 UI/UX 설계 (신규)**

대회 상세 페이지를 **에어비앤비 숙소 상세 / 인터파크 공연 상세**와 동일한 2단 레이아웃으로 전면 재설계한다. 이 구조에서 대회 상세 페이지가 신청 플로우의 **1단계(디비전 선택)**까지 담당하게 된다.

#### 데스크탑 레이아웃

```
┌─────────────────────────┬───────────────────────┐
│  왼쪽 (스크롤됨)         │  오른쪽 (sticky 고정)  │
│                         │                       │
│  포스터 이미지           │  대회명, 날짜, 장소    │
│  대회 설명               │  상태 뱃지             │
│  규칙 / 운영 방식        │  ──────────────────   │
│  (길면 스크롤)           │  디비전 카드 목록       │
│                         │  (클릭 시 선택 하이라이트)│
│                         │  ──────────────────   │
│                         │  [신청하기] CTA 버튼   │
└─────────────────────────┴───────────────────────┘
```

- 오른쪽 패널: `position: sticky; top: 2rem; max-height: calc(100vh - 4rem); overflow-y: auto` — 디비전이 많아도 패널 내부에서만 스크롤
- 디비전 카드 클릭 → 선택 하이라이트, CTA 버튼 활성화 (카드마다 개별 버튼 없음)
- 왼쪽 콘텐츠가 짧아 오른쪽 패널이 어색하게 뜨는 경우를 대비해 왼쪽에 최소 높이 또는 단일 컬럼 fallback 처리 필요

#### 모바일 레이아웃

```
[포스터 이미지]
[대회 기본 정보]
[디비전 목록 — 읽기용, 선택 불가]
[대회 설명]

─────────────────────────  (화면 하단 고정 바)
[디비전 선택됨: 일반부]  [신청하기 →]
```

- 하단 고정 바(fixed bottom bar)에 현재 선택된 디비전명 + "신청하기" 버튼 배치
- "신청하기" 버튼 탭 → **바텀시트** 슬라이드업 — 디비전 카드 목록 표시, 선택 후 다음 단계 진행
- **디비전이 1개**인 경우: 바텀시트 없이 바로 신청 페이지로 이동 (불필요한 탭 제거)
- **이미 신청된** 경우: CTA가 "신청 현황 보기"로 변경, 신청된 디비전 카드에 뱃지 표시

#### 신청 플로우 재설계 (현재 → 목표)

```
[현재]
대회 상세 → /apply (디비전 + 팀 + 로스터 한 페이지)

[목표]
대회 상세 (디비전 선택)
  → /apply?division=xxx (팀 선택 + 로스터 제출만)
    → /my-applications/[id] (신청 완료 — 입금 계좌 즉시 노출)
```

이 구조로 각 화면의 결정 부담이 분리된다:
- 대회 상세: "어떤 대회의 어떤 부문?" → 읽고 결정
- 신청 페이지: "어떤 팀으로, 누구와?" → 실행
- 완료 페이지: 입금 안내 즉시 확인

### STEP 3. 참가 자격 체크

**현재**: `app/(app)/tournament/[id]/apply/page.tsx`

**구현된 것:**
- 로그인 여부 확인 → `/login` 리다이렉트
- `isUserRole` 확인 → `/onboarding/profile` 리다이렉트 (프로필 미완성 차단)
- 이미 신청된 경우 → `/my-applications/[id]` 리다이렉트

**없는 것 (미구현) — 이 단계가 가장 부실함:**

#### 3-1. 본인인증 여부 미체크
`profiles.identity_verified_at` 컬럼이 존재하고(`0219_identity_verifications.sql`) 본인인증 플로우도 구현되어 있으나, 신청 페이지(`apply/page.tsx`)에서 `identity_verified_at IS NULL` 사용자를 **전혀 차단하지 않음**.

```typescript
// apply/page.tsx 현재 로직 — identity_verified_at 체크 없음
const userResult = await getUserWithRole();
if (userResult.status === "unauthenticated") redirect("/login");
if (isUserRole(userResult.role)) redirect("/onboarding/profile");
// 여기서 identity_verified_at 체크가 빠져 있음
```

운영자가 본인인증 필수 대회를 설정하더라도 미인증 사용자가 신청 가능한 상태.

#### 3-2. division 단위 참가 자격 조건 없음
현재 `divisions` 테이블에 자격 조건 컬럼 자체가 없음:
- 나이 제한 (min_age, max_age) 없음
- 성별 제한 (gender: 'male'|'female'|'mixed') 없음
- 실력 등급 제한 (skill_level) 없음
- 특정 지역 팀만 참가 가능 등의 조건 없음

신청 서버 액션(`applyToTournament`)에서도 division 자격 조건 검증 로직 전무.

#### 3-3. 중복 출전 방지 — 팀 단위만 처리
`submit_tournament_application` RPC에서 `(team_id, division_id)` partial unique index로 팀 단위 중복 방지는 처리됨. 그러나 **동일 선수가 다른 팀으로 같은 대회 다른 division에 로스터로 등록되는 것은 방지하지 않음** (add_roster_member RPC에서 roster_id 기준 중복만 체크, tournament 단위 중복 출전은 별도 체크 없음).

#### 3-4. 신청 마감일 서버 검증 없음
`divisions.application_close_at` 컬럼이 드롭됨(`0240_drop_division_application_dates.sql`). 신청 가능 여부는 `tournaments.status = 'open'` 하나로만 판단. 운영자가 수동으로 `status`를 'closed'로 바꾸기 전까지는 계속 신청 가능.

### STEP 4. 팀 선택 + 최소 로스터 제출 (신청 페이지)

> **플로우 재설계에 따른 변경**: 디비전 선택은 대회 상세 페이지로 이동. `/apply` 페이지는 `?division=xxx` URL 파라미터로 디비전을 받아서 팀 선택과 로스터 제출만 담당한다.

**현재**: `app/(app)/tournament/[id]/apply/Form.tsx` — 디비전 + 팀 + 로스터 한 화면에서 모두 처리

**목표 구조**:

```
/apply?division=xxx
┌─────────────────────────────────────────┐
│  선택된 디비전 요약 카드 (읽기 전용)      │  ← 대회 상세에서 넘어온 값, 변경하려면 뒤로
│  ──────────────────────────────────── │
│  팀 선택 (captain인 팀만)               │
│  ──────────────────────────────────── │
│  로스터 선택 (RosterPicker)             │
│  N명 선택됨 / 최소 M명 이상 필요        │  ← 인원 카운터 + 최소 인원 가이드
│  ──────────────────────────────────── │
│  [신청하기] (최소 인원 미달 시 비활성)  │
└─────────────────────────────────────────┘
```

**구현된 것:**
- captain 역할인 팀 목록 드롭다운 선택
- 선택한 팀의 현재 활성 신청이 있으면 해당 팀 신청 불가 표시
- RosterPicker로 팀원 선택 가능

**없는 것 (미구현):**
- URL `?division=xxx` 파라미터 수신 및 디비전 요약 카드 표시 (현재는 Form 내부에서 division 선택)
- 디비전 파라미터 없을 때 대회 상세로 리다이렉트하는 가드
- division별 정원 현황 표시 (남은 자리 N개, 대기 중 N팀)
- 내가 선택한 팀이 이미 다른 division에 신청한 경우 경고

### STEP 5. 최소 로스터 제출

**현재**: `applyWithRosterAction` + Form의 `RosterPicker`

**구현된 것:**
- 신청과 동시에 로스터 선택 가능 (RosterPicker)
- 선수 선택 없이도 신청 완료 처리 (`memberIds.length === 0` → `return { ok: true }`)
- 팀원 목록을 팀별로 미리 로드 (`teamMembersMap`)

**없는 것 (미구현) — 실질적으로 최소 로스터 강제가 없음:**

#### 5-1. 최소 인원 강제 없음
`divisions` 테이블에 `min_roster_size` 컬럼이 없고, `applyWithRosterAction`에서도 인원 수를 검증하지 않음:

```typescript
// actions.ts 현재 코드
if (input.memberIds.length === 0) {
  return { ok: true, applicationId }; // ← 0명으로 신청 완료됨
}
```

로스터 없이 신청 완료가 가능하여 "최소 로스터 제출" 요구사항이 실질적으로 미구현 상태.

#### 5-2. 최대 인원 강제 없음
`roster_members` 테이블에 최대 인원 제약 없음. `add_roster_member` RPC도 `max_roster_size`를 체크하지 않음.

#### 5-3. UI에서 최소 인원 가이드 없음
Form.tsx의 RosterPicker에서 "N명 이상 선택 필요" 안내 문구 없음. 선택 인원 수 표시도 없음.

#### 5-4. 사후 로스터 추가는 가능하나 흐름이 분리됨
신청 후 `my-applications/[applicationId]` 페이지에서 로스터 수정 가능. 그러나 초기 신청 시 로스터 미제출 상태로 `payment_pending`에 들어가면, 운영자는 로스터 없이 입금 안내를 진행해야 하는 구조.

### STEP 6. 신청 완료

**현재**: `Form.tsx` 성공 처리 + `/my-applications/${applicationId}` 리다이렉트

**구현된 것:**

## 7. 구현 시 주의사항

### 7-1. 본인인증 체크 위치 — server-side 강제 필요

`apply/page.tsx`에서 `getUserWithRole()` 결과에 `identity_verified_at` 필드가 포함되어 있지 않음. `profiles` 테이블을 별도로 조회하거나 `getUserWithRole()`이 반환하는 타입을 확장해야 함. 클라이언트에서만 체크하면 우회 가능하므로 반드시 서버 컴포넌트 또는 서버 액션에서 강제해야 함.

### 7-2. 최소 로스터 강제 시점 — 신청 시 vs 마감 시

두 가지 전략 선택 필요:
- **신청 시 강제**: 최소 인원 미달 시 신청 자체를 거부 → 사용자가 즉시 멤버 추가 필요
- **마감 전 경고**: 신청은 허용하되, 로스터 마감 전까지 최소 인원 미달 시 경고 표시

현재 프로젝트의 흐름(신청 → 입금 → 로스터 수정 가능)을 고려하면, **신청 시 최소 1명 이상 강제 + 마감 전 N명 미달 경고** 혼합 방식이 현실적.

### 7-3. 대회 상세 sticky 패널 — 왼쪽 콘텐츠 짧을 때 처리

오른쪽 패널이 `position: sticky`로 고정될 때, 왼쪽 포스터/설명 콘텐츠가 오른쪽 패널보다 짧으면 패널이 어색하게 떠있는 상황이 발생한다. 대처 방법:
- 왼쪽 콘텐츠 영역에 `min-h` 최솟값 설정 (예: 오른쪽 패널 예상 높이 이상)
- 또는 콘텐츠가 일정 길이 미만이면 단일 컬럼으로 fallback (CSS `@container` 또는 조건부 렌더링)
- description 필드가 DB에 아직 없으므로, 추가 전까지는 왼쪽이 포스터 이미지만 될 수 있어 이 문제가 먼저 발생한다.

### 7-4. 모바일 바텀시트 — 디비전 1개 예외 처리

디비전이 1개인 대회에서 "신청하기" 탭 시 바텀시트 없이 바로 `/apply?division=xxx`로 이동해야 한다. 바텀시트를 띄우는 로직에서 `divisions.length === 1` 조건 분기 필수. 그렇지 않으면 디비전 1개짜리 대회마다 불필요한 탭이 발생한다.

### 7-5. 신청 완료 후 리다이렉트 위치

현재 `applyWithRosterAction` 성공 후 `router.push('/my-applications/${applicationId}')`로 이동. 재설계 목표상 이 페이지가 신청 완료 화면 역할도 해야 하므로, `?from=apply` 파라미터를 추가해 최초 진입 시 **입금 계좌 정보를 상단에 크게 노출**하는 UI 분기를 두는 것이 좋다.

### 7-6. `result/page.tsx`의 `getTournamentBracketMatches` — 그룹 경기 포함 여부

현재 함수명이 "bracket"이므로 그룹 스테이지 경기가 제외될 가능성 있음. 함수 내부 쿼리 조건(`match_type`, `stage` 등)을 확인하고, 그룹 경기를 별도 섹션으로 표시하는 구조 추가 필요.

### 7-7. 대회 목록 N+1 쿼리 문제

카드별 신청 수, 정원을 표시하면 N+1 쿼리 발생. `listAllMyTeamApplications()`로 한 번에 가져와서 프론트에서 매핑하는 방식 권장 (이미 함수 존재).

### 7-8. `closed` 상태 레이블 불일치 (기존 이슈)

관리자 화면: "진행중" / 사용자 화면: "모집마감"으로 혼용 중. 대회 목록 탭에서 정책 통일 필요.

## 9. 결론

### 전체 플로우 구현 상태 요약

| 단계 | 현재 상태 | 핵심 GAP |
|---|---|---|
| 대회 목록 | 탭·검색·필터·카드·신청상태 매핑 대부분 구현됨 | TournamentCard 내부 참가비/정원 표시 여부 확인, 지역 필터 미구현 |
| 대회 상세 | 단일 컬럼 기본 표시만 | 2단 sticky 레이아웃, 모바일 바텀시트, 대회 설명/포스터, 디비전 선택 인터랙션 전무 |
| **참가 자격 체크** | **가장 부실 — 본인인증 미체크, 자격 조건 DB 없음** | identity_verified_at 체크, min_roster_size, division 자격 조건 |
| 팀 선택 + 디비전 선택 | apply 한 페이지에 혼재 | 디비전 선택을 상세 페이지로 분리, 신청 페이지 단순화 필요 |
| **최소 로스터 제출** | **강제 없음 — 0명으로 신청 완료 가능** | min_roster_size 서버 검증 |
| 신청 완료 | 리다이렉트만 | 알림 발송 없음, 입금 계좌 즉시 안내 없음 |
| 입금/승인 상태 확인 | DB 인프라 완성, UI 미흡 | 카운트다운, "입금 완료" 버튼, 대기 순번 |
| 로스터 수정 마감 | start_date 기준 잠금만 | 커스텀 마감일, 마감 전 알림 없음 |
| 일정/대진/결과 | 결과 페이지 있음 | 내 팀 필터, 일정 뷰, 조별리그, 실시간 스코어 없음 |

### 가장 취약한 세 단계

**1위: 대회 상세 UI/UX (STEP 2)**

현재 단일 컬럼 레이아웃으로는 포스터, 설명, 디비전 선택, CTA가 한 줄로 쌓여 있어 사용자가 정보를 읽으면서 동시에 신청 결정을 내리기 어렵다. 2단 sticky 레이아웃과 모바일 바텀시트로 재설계하면 신청 전환율과 UX 모두 개선된다. 또한 이 페이지에서 디비전 선택까지 처리해야 이후 apply 페이지가 단순해지므로, 플로우 전체의 기반이 되는 작업이다. `tournaments.description` DB 컬럼이 없어 설명 영역 자체가 비어있는 문제도 함께 해결해야 한다.

**2위: 참가 자격 체크 (STEP 3)**

본인인증 여부를 신청 페이지에서 전혀 검증하지 않아 미인증 사용자가 신청 가능한 상태다. `identity_verified_at` 컬럼과 인증 플로우는 이미 구현되어 있으므로 apply/page.tsx에 체크 로직만 추가하면 되나, `getUserWithRole()` 반환 타입에 해당 필드가 없어 별도 쿼리가 필요하다. division별 자격 조건(나이, 성별)은 DB 자체가 없어 장기 과제다.

**3위: 최소 로스터 제출 (STEP 5)**

현재 로스터 0명으로도 신청이 완료된다. `divisions.min_roster_size`가 없으므로 DB 마이그레이션 → API 타입 수정 → 서버 액션 검증 → Form UI 안내 순으로 전 레이어에 걸쳐 작업이 필요하다.

### 후속 확장 포인트

1. **선수별 중복 출전 방지**: roster 등록 시 동일 선수가 같은 대회 다른 팀/division에 등록되는 것 방지
2. **대회 설명/규칙**: `tournaments.description` 필드 추가 및 상세 페이지 왼쪽 영역에 표시
3. **알림 시스템 활성화**: notifications 테이블은 있으나 실제 INSERT 로직 전무 — 각 상태 전환 지점에 추가 필요
4. **실시간 스코어**: Supabase Realtime 구독 또는 polling 기반 라이브 스코어 표시
5. **division별 자격 조건**: 나이·성별·지역 제한 — DB 마이그레이션부터 장기 과제
