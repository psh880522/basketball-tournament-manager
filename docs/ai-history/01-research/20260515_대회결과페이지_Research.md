# 대회 결과 페이지 리서치

> 요구사항 원문  
> 대회 결과 페이지를 만들려고 해. 비슷한 서비스 5개 정도 벤치마킹해서 어떤 식으로 만들면 좋을지 리서치해줘.

---

## 기능 개요

공개 대회 결과 페이지(`/tournament/[id]/result`)를 시각적으로 완성된 형태로 리뉴얼한다.  
현재 페이지는 인라인 스타일로만 구성된 프로토타입 수준이며, 브래킷 시각화 없음, 모바일 미대응, 정보 구조가 단순 텍스트 나열에 그친다.

---

## 구현 목표

- 대진표(토너먼트 브래킷)를 시각적 트리 구조로 보여줄 수 있다
- 조별 리그 순위를 디비전/그룹별 테이블로 보여줄 수 있다
- 우승팀을 챔피언 배너로 강조 표시할 수 있다
- 탭 방식으로 "대진표"와 "조별 순위"를 전환할 수 있다
- 모바일에서 브래킷은 수평 스크롤, 순위표는 핵심 컬럼만 표시한다
- 모든 스타일을 인라인 style에서 Tailwind CSS로 교체한다

## 벤치마킹 분석 (5개 서비스)

### 1. Challonge (challonge.com)

**특징**
- 좌→우 트리 구조의 수평 브래킷 레이아웃 (가장 보편적인 표준)
- 매치 카드: `팀명 | 점수` 한 줄, 승자는 굵게 표시
- Round Robin 경우 브래킷 하단에 순위표 추가 표시
- 실시간 브래킷 업데이트 지원

**약점**
- 모바일 UX가 가장 나쁜 서비스 중 하나 (커뮤니티 평가: "cramped")
- 쿼터별 스코어 미표시

**차용할 패턴**: 좌→우 수평 브래킷 트리 레이아웃, 매치 카드 구조

---

### 2. BracketHQ (brackethq.com)

**특징**
- Dark/Light/Card 등 다수 테마 지원
- Pool Play + Elimination 혼합 방식 완벽 지원 (조별리그 → 토너먼트)
- 스코어 제출 즉시 순위표와 브래킷이 실시간 갱신
- 모든 기기에서 반응형 레이아웃 작동

**약점**
- 선수 개인 통계 없음
- 한국어 미지원

**차용할 패턴**: Pool Play(조별) + 토너먼트 탭 분리 방식, 반응형 카드 레이아웃

---

### 3. FIBA 공식 홈페이지 (fiba.basketball)

**특징**
- Standings / Bracket / Classification Games / Results 탭 완전 분리
- MVP 및 주요 수상자 섹션 (덴니스 슈뢰더 등 MVP 카드 형식)
- Leaders 탭: 득점/리바운드/어시스트 상위 선수 별도 표시
- 각 매치 카드에 날짜, 라운드, 최종 스코어 + "More" 상세 링크

**약점**
- 팀 코드(3자리 ISO)를 사용해 소규모 대회에 그대로 적용 어려움
- 모바일 최적화 제한적

**차용할 패턴**: 챔피언/MVP 배너, 탭 기반 정보 구조, 라운드별 매치 카드

---

### 4. 다음스포츠 / KBL (sports.daum.net/record/kbl)

**특징**
- 한국 농구 표준 순위표 컬럼: `순위 | 팀 | 경기 | 승 | 패 | 승률 | 게임차 | 홈/원정 | 연속`
- 쿼터별 스코어(Q1 Q2 Q3 Q4 + 최종) 표시
- 선수 카드: 사진 + 팀 로고 + 이름/팀명 형식
- 팀별 팀통계(득점/리바운드/어시스트/스틸/블록/슈팅%) 동시 제공

**약점**
- 소규모 대회용 브래킷 시각화 없음 (리그 전용)
- 프로팀 전용이라 소규모 대회에 과도한 정보량

**차용할 패턴**: 한국 표준 순위 컬럼, 1~3위 강조 표시, 순위 뱃지 색상 (금/은/동)

## 3. 현재 구현 상태

### 공개 결과 페이지 (`app/(app)/tournament/[id]/result/page.tsx`)

**현재 상태**: 프로토타입 수준의 기능적 구현만 완료. UI 완성도 없음.

**구조 요약:**
```
ResultContent (서버 컴포넌트)
  ├── getPublicTournamentById()      → 대회명, 날짜, 장소
  ├── getTournamentBracketMatches()  → 토너먼트 단계 경기 전체
  ├── getDivisionsWithGroups()       → 디비전 + 그룹 목록
  ├── getUserWithRole()              → 주최자 여부 확인
  └── getStandingsByGroup() (for each group) → 그룹별 순위

렌더링 섹션:
  1. 대회 헤더 (이름, 기간, 장소) - 인라인 스타일
  2. 우승팀 - 단순 텍스트
  3. 토너먼트 결과 - 라운드별 박스 카드 (브래킷 없음)
  4. 조별 순위 - 텍스트 나열
```

**현재 버그 / 개선 필요사항:**
1. **디비전 미분리**: `getTournamentBracketMatches`는 전체 토너먼트의 브래킷 매치를 반환하는데, 현재 코드는 `division_id`로 분리하지 않고 라운드(`group.name`)만으로 묶음. 디비전이 여러 개일 경우 모든 디비전의 경기가 혼합 표시됨.
2. **그룹 타입 미필터**: `getDivisionsWithGroups`는 league 그룹과 tournament 그룹을 모두 반환. 순위표 조회 시 tournament 그룹에 대해 빈 standings를 조회하는 낭비 발생.
3. **인라인 스타일 전체 사용**: 프로젝트 전체 스타일 패턴(Tailwind)과 불일치.
4. **브래킷 시각화 없음**: 텍스트 목록 형태로만 표시.
5. **모바일 미대응**: 반응형 클래스 없음.
6. **탭 없음**: 브래킷과 순위가 스크롤로만 분리됨.

### 5-2. 서버 액션 / API

**신규 API 함수 필요 여부:**

현재 `getDivisionsWithGroups`는 league + tournament 그룹 모두 반환. 두 가지 해결 방안:

**방안 A (권장)**: 클라이언트에서 group type 필터링  
→ API 수정 없이 page.tsx에서 league 그룹만 필터  
→ 현재 standings 테이블에서 `group_id`가 있는 rows만 조회해도 league 그룹임을 알 수 있음

**방안 B**: `getDivisionsWithLeagueGroups` 신규 함수  
→ `supabase.from("groups").select("id,name,order,type").eq("division_id", divId).eq("type", "league")` 추가  
→ API 수정 범위 최소화를 위해 방안 A 권장

**브래킷 데이터 분리:**  
현재 `getTournamentBracketMatches(tournamentId)`는 전체 반환.  
page.tsx에서 `division_id`로 그룹화 후 각 디비전별 브래킷 렌더링 필요:
```typescript
const bracketByDivision = new Map<string, TournamentBracketMatchRow[]>();
bracketMatches.forEach((match) => {
  const arr = bracketByDivision.get(match.division_id) ?? [];
  arr.push(match);
  bracketByDivision.set(match.division_id, arr);
});
```

### 5-4. DB / 마이그레이션

**신규 마이그레이션 없음.** 기존 스키마로 충분.

관련 테이블:
```sql
matches          -- score_a, score_b, winner_team_id, status, group_id (→ groups.type = 'tournament')
standings        -- group_id(nullable), wins, losses, points_for, points_against, rank
divisions        -- id, name, tournament_id, standings_dirty
groups           -- id, name, order, type ('league' | 'tournament'), division_id
tournaments      -- id, name, status, start_date, end_date, location
teams            -- id, team_name, tournament_id
```

### 5-5. 권한 정책 (RLS)

**기존 RLS로 모두 커버. 신규 정책 불필요.**

`0078_tournament_result_public_rls.sql` 기준:

```sql
-- matches: 공개 읽기 (tournament.status IN ('closed', 'finished'))
matches_select_public_finished

-- standings: 공개 읽기
standings_select_public_closed

-- divisions: 공개 읽기
divisions_select_public_closed

-- groups: 공개 읽기 (divisions → tournaments 조인)
groups_select_public_closed

-- teams: 공개 읽기 (group_teams → groups → divisions → tournaments 조인)
teams_select_public_closed
```

주최자(organizer) 접근: 별도 정책 `0085_tournaments_select_organizer_all.sql`로 모든 상태 접근 가능.  
`getUserWithRole()`으로 role을 확인하고, organizer이면 tournament.status와 무관하게 결과 페이지 표시.

## 7. 구현 시 주의사항

### 1. 디비전 복수 처리 (현재 버그)
`getTournamentBracketMatches`는 전체 토너먼트의 브래킷 매치를 반환.  
복수 디비전이 있을 경우 `division_id`로 먼저 그룹화한 뒤 각각 브래킷 렌더링.  
현재 코드는 이 처리가 없어 디비전 이름 구분 없이 섞임.

### 2. League 그룹 필터링
`getDivisionsWithGroups`가 league + tournament 그룹을 모두 반환.  
순위표 탭에서는 `group.type === 'league'` 그룹에 대해서만 `getStandingsByGroup` 호출.  
현재 `page.tsx`는 모든 그룹에 대해 순위를 조회하고 빈 결과를 조용히 무시함 (비효율).

### 3. 챔피언 결정 로직
`final` 그룹 이름의 매치에서 `winner_team_id`를 확인.  
`winner_team_id === team_a.id` → `team_a.team_name`, 아니면 `team_b.team_name`.  
복수 디비전의 경우 각 디비전의 결승이 별도로 존재하므로 디비전별 우승팀 배너 렌더링.

### 4. TBD 슬롯 처리
브래킷에서 아직 배치되지 않은 팀(`team_a = null` 또는 `team_b = null`):
- 팀명 자리에 "미정" 표시
- 점수 자리에 "-" 표시
- 연결선은 유지 (트리 구조 유지)

### 5. 3/4위전 위치
브래킷 트리에서 3/4위전(`third_place`)은 결승 전 라운드(준결승)와 같은 열에 배치하거나  
결승 옆에 작은 카드로 배치. FIBA 방식처럼 별도 섹션으로 분리하는 것도 가능.  
현재 `roundOrder`는 `["round_of_16", "quarterfinal", "semifinal", "third_place", "final"]`.

### 6. 접근 제어 조건
```typescript
const isPublicVisible = tournament.status === "closed" || tournament.status === "finished";
// organizer는 항상 접근 가능
if (!isOrganizer && !isPublicVisible) { return <접근 불가 메시지> }
```
`open` 상태 대회의 결과 페이지를 일반 유저가 접근하면 접근 불가 메시지 표시.

### 7. Suspense 경계
현재 `ResultContent`를 `<Suspense fallback={...}>`으로 감싸고 있음. 유지 권장.  
데이터 로딩 중 상태를 보여주는 적절한 스켈레톤 UI 추가 권장.

### 8. RLS 통과 조건
공개 결과 페이지에서 로그아웃 상태로 접근 시, Supabase anon key로 쿼리 실행.  
`tournament.status IN ('closed', 'finished')`여야만 RLS 통과.  
organizer가 `open` 상태 대회를 미리 보는 경우: service role이 아닌 user session으로 조회되어야 함 → `getUserWithRole()`이 session 기반이므로 정상 작동.

## 9. 결론

현재 공개 결과 페이지는 기능은 작동하나 **시각적 완성도가 매우 낮은 프로토타입** 수준이다.

**벤치마킹 핵심 교훈:**
- Challonge의 좌→우 수평 브래킷 트리는 가장 직관적인 표준이다 (차용)
- 다음스포츠/KBL의 한국 표준 순위 컬럼을 그대로 사용한다 (순위|팀|경기|승|패|득실차)
- Challonge의 모바일 실패를 반면교사 삼아 수평 스크롤 브래킷을 설계한다
- FIBA의 탭 분리 방식(대진표/순위)을 도입한다
- Start.gg의 1/2/3위 플레이스먼트 카드를 챔피언 배너에 적용한다

**기존 코드에서 수정이 필요한 버그:**
1. `division_id` 미분리로 복수 디비전 결과가 혼합 표시되는 버그
2. league/tournament 그룹 미구분으로 불필요한 standings 쿼리 발생

**신규 DB 마이그레이션은 불필요**. 기존 스키마와 RLS로 모든 요구사항 충족.  
**신규 API 함수도 불필요**. 기존 API 재조합으로 구현 가능.

주요 신규 작업은 `result/components/` 하위 4개 컴포넌트 작성과  
`page.tsx`의 Tailwind 전환 + 데이터 로딩 로직 개선에 집중된다.
