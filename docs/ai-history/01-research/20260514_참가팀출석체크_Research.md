# 참가팀 출석 체크 리서치

> 요구사항 원문  
> 참가팀 리스트 페이지를 만들어서 대회 운영 단계 중 스케줄 다음 단계에 넣어서 경기 시작 전 팀 출석 체크를 하고 싶어.  
> 경기 생성 이후라 디비전/조별/팀명/주장이름/연락처/출석여부(체크) 이정도 정보가 보여졌으면 좋겠어.  
> 그리고 엑셀로 export할 수 있었으면 좋겠어.

---

## 기능 개요

대회 당일 경기 시작 전, 운영자가 참가 확정 팀의 출석 여부를 체크하는 페이지.  
`/admin/tournaments/[id]/attendance`에 위치하며, 기존 5단계 운영 플로우(팀 승인 → 경기 생성 → 스케줄 → **출석 체크** → 결과 → 종료)에 새 단계로 삽입된다.

---

## 구현 목표

- 운영자가 참가 확정 팀(status = confirmed) 목록을 디비전/조별로 조회할 수 있다
- 각 팀 행에서 디비전명, 조명, 팀명, 주장이름, 연락처, 출석여부(체크박스)를 확인할 수 있다
- 운영자가 출석 체크(토글)를 하면 DB에 즉시 반영된다
- 전체 팀 목록을 Excel 파일로 내보낼 수 있다
- 대회 운영 대시보드에 "출석 체크" 단계가 스케줄과 결과 사이에 표시된다

---

## 상태 / 플로우 정의

### 현재 운영 플로우 (5단계)
```
팀 승인 → 경기 생성 → 스케줄 → 결과 → 종료
```

### 변경 후 운영 플로우 (6단계)
```
팀 승인 → 경기 생성 → 스케줄 → 출석 체크 → 결과 → 종료
```

### TournamentProgressState 변경
```typescript
// lib/api/tournamentProgress.ts
type TournamentProgressState =
  | "TEAM_APPROVAL"
  | "MATCH_GENERATION"
  | "SCHEDULE"
  | "ATTENDANCE_CHECK"   // ← 신규 추가
  | "RESULT"
  | "TOURNAMENT_FINISHED";
```

### 출석 체크 단계 활성화 조건
- `scheduledMatches === totalMatches && totalMatches > 0` → SCHEDULE 완료 → ATTENDANCE_CHECK 진입
- 출석 체크 자체는 "완료" 상태 없음 (선택적 단계이므로 체크 여부와 무관하게 RESULT로 넘어갈 수 있음)
- 단, 대시보드에서 "출석 체크" 카드는 스케줄 완료 후 `active` 상태로 표시됨

## 주요 규칙 및 제약

1. **조회 대상**: `tournament_team_applications.status = 'confirmed'` 인 팀만 표시
2. **조(group) 정보**: `group_teams` → `groups` JOIN으로 획득. `groups.type = 'league'`인 그룹만 표시 (토너먼트 브래킷 그룹 제외)
3. **주장 이름**: `teams.captain_user_id` → `profiles.display_name`. display_name이 null이면 빈 문자열로 표시
4. **연락처**: `teams.contact` (팀 생성 시 입력된 연락처 사용)
5. **출석 여부**: 신규 `team_attendance` 테이블 (tournament_id + team_id PK). 행 존재 + attended = true = 출석
6. **RLS**: team_attendance는 organizer만 INSERT/UPDATE 가능, SELECT는 organizer만
7. **Excel 정렬**: 디비전 sort_order → 조 order → 팀명 alphabetically
8. **출석 토글**: 서버 액션으로 처리 (optimistic update 적용)

### 5-4. DB / 마이그레이션

**신규 마이그레이션**: `supabase/migrations/0255_team_attendance.sql`

```sql
CREATE TABLE public.team_attendance (
  tournament_id uuid NOT NULL REFERENCES public.tournaments(id) ON DELETE CASCADE,
  team_id       uuid NOT NULL REFERENCES public.teams(id) ON DELETE CASCADE,
  attended      boolean NOT NULL DEFAULT false,
  checked_by    uuid REFERENCES auth.users(id) ON DELETE SET NULL,
  checked_at    timestamptz,
  PRIMARY KEY (tournament_id, team_id)
);
```

**조회 쿼리 전략**:
```sql
SELECT
  t.id AS team_id,
  t.team_name,
  d.id AS division_id,
  d.name AS division_name,
  d.sort_order AS division_sort_order,
  g.id AS group_id,
  g.name AS group_name,
  g.order AS group_order,
  p.display_name AS captain_name,
  t.contact,
  COALESCE(ta.attended, false) AS attended
FROM tournament_team_applications tta
JOIN teams t ON t.id = tta.team_id
JOIN divisions d ON d.id = tta.division_id
LEFT JOIN group_teams gt ON gt.team_id = t.id
LEFT JOIN groups g ON g.id = gt.group_id AND g.type = 'league'
LEFT JOIN profiles p ON p.id = t.captain_user_id
LEFT JOIN team_attendance ta ON ta.tournament_id = tta.tournament_id AND ta.team_id = t.id
WHERE tta.tournament_id = $1
  AND tta.status = 'confirmed'
ORDER BY d.sort_order, g.order NULLS LAST, t.team_name
```

> ⚠️ Supabase JS SDK로 위 JOIN을 표현하기 어려울 수 있음. `supabase.rpc()` 또는 직접 `.from('tournament_team_applications').select(...)` 체인으로 처리 방식 결정 필요.

### 5-5. 권한 정책 (RLS)

**신규 RLS (team_attendance 테이블)**

```sql
-- SELECT: organizer만
ALTER TABLE public.team_attendance ENABLE ROW LEVEL SECURITY;

CREATE POLICY "attendance_select_organizer" ON public.team_attendance
  FOR SELECT USING (public.is_organizer());

CREATE POLICY "attendance_insert_organizer" ON public.team_attendance
  FOR INSERT WITH CHECK (public.is_organizer());

CREATE POLICY "attendance_update_organizer" ON public.team_attendance
  FOR UPDATE USING (public.is_organizer()) WITH CHECK (public.is_organizer());

  FOR DELETE USING (public.is_organizer());
```

## 7. 구현 시 주의사항

### 7-1. 그룹 JOIN 중복 주의
팀이 `group_teams`에 league 그룹과 tournament 그룹 양쪽에 등록될 수 있음.  
반드시 `groups.type = 'league'` 필터를 걸어야 한다. LEFT JOIN이므로 경기 생성 전이면 group_name이 null.

### 7-2. Supabase JS SDK의 JOIN 한계
복잡한 다중 테이블 JOIN은 Supabase JS SDK의 `select()` 체인으로 표현이 제한적.  
`supabase.rpc('get_teams_with_attendance', { p_tournament_id: id })` 방식 또는  
SDK에서 가능한 범위에서 처리 후 메모리에서 병합하는 방식 중 선택.  
→ **권장: SDK select chain으로 가능한 한 처리, 복잡하면 rpc로 전환**

### 7-3. TournamentProgressState 상태 전환 로직
`resolveState()` 현재 코드:
```typescript
if (summary.scheduledMatches < summary.totalMatches) return "SCHEDULE";
return "RESULT";
```
수정 후:
```typescript
if (summary.scheduledMatches < summary.totalMatches) return "SCHEDULE";
return "ATTENDANCE_CHECK";  // 스케줄 완료 후 출석 체크로 전환
// RESULT는 출석 체크 페이지에서 "결과 입력" 버튼으로 이동
```
> ⚠️ 출석 체크는 필수가 아니므로 "완료" 조건 없이 항상 active. 결과 입력 페이지는 attendance 페이지의 "결과 입력으로" 버튼 또는 대시보드에서 직접 접근 가능하게 유지.

### 7-4. Excel export 방식
- 서버 사이드에서 `xlsx` 패키지로 Buffer 생성 → API route에서 응답
- 클라이언트에서 `<a>` 태그 download 트리거 방식 사용
- API route 경로: `GET /api/admin/tournaments/[id]/attendance/export`
- 인증: Supabase session cookie 기반 (서버에서 `createSupabaseServerClient()` 사용)

### 7-5. ProgressIndicator 스텝 수 변경
현재 `lg:grid-cols-3` (5개 스텝에 최적화). 6개 스텝이 되면 레이아웃 검토 필요.  
`sm:grid-cols-2 lg:grid-cols-3`은 6개에서도 2행 3열로 맞아떨어지므로 그대로 사용 가능.

## 9. 결론

출석 체크 기능은 기존 6단계 플로우에 새 단계를 삽입하는 작업으로,  
**신규 테이블 1개**, **신규 파일 5개**, **수정 파일 4개**가 필요하다.

핵심 복잡도는 두 곳:
1. **다중 JOIN 쿼리**: teams + applications + divisions + groups + profiles + attendance를 하나의 쿼리로 가져오는 것 → Supabase SDK 한계 고려해 구현 방식 선택 필요
2. **TournamentProgressState 상태 머신 수정**: SCHEDULE → ATTENDANCE_CHECK 전환 조건 및 RESULT 진입 경로 보존

Excel export는 `xlsx` 패키지 + API route 조합으로 구현하는 것이 Next.js App Router 환경에서 가장 자연스럽다.
