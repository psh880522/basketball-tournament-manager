## 3. Phase별 구현 계획

### Phase 1. DB 스키마 / 마이그레이션 + RLS

**파일**: `supabase/migrations/0255_team_attendance.sql`

#### 신규 테이블: `team_attendance`

| 컬럼 | 타입 | 제약 | 설명 |
|------|------|------|------|
| `tournament_id` | uuid | NOT NULL, FK → tournaments.id ON DELETE CASCADE | 대회 ID |
| `team_id` | uuid | NOT NULL, FK → teams.id ON DELETE CASCADE | 팀 ID |
| `attended` | boolean | NOT NULL DEFAULT false | 출석 여부 |
| `checked_by` | uuid | FK → auth.users(id) ON DELETE SET NULL | 체크한 운영자 |
| `checked_at` | timestamptz | nullable | 체크 시각 |
| PK | — | `(tournament_id, team_id)` | 복합 PK |

#### 인덱스
- `idx_team_attendance_tournament` ON `team_attendance(tournament_id)` — 대회별 조회 최적화

#### RLS 정책 (4개)

| 정책명 | 작업 | 조건 |
|--------|------|------|
| `attendance_select_organizer` | SELECT | `is_organizer()` |
| `attendance_insert_organizer` | INSERT | `is_organizer()` |
| `attendance_update_organizer` | UPDATE | `is_organizer()` |
| `attendance_delete_organizer` | DELETE | `is_organizer()` |

#### 롤백 방법
```sql
DROP TABLE IF EXISTS public.team_attendance;
```
마이그레이션 단독이므로 위 한 줄로 롤백 가능. CASCADE로 인해 연관 데이터 없음.

### Phase 3. 서버 액션 / API

#### 3-1. `lib/api/attendance.ts`

**`getTeamsWithAttendance(tournamentId: string): Promise<ApiResult<AttendanceRow[]>>`**

의사코드:
```
1. createSupabaseServerClient() 호출
2. tournament_team_applications에서 status = 'confirmed', tournament_id = tournamentId 조회
   → select: id, team_id, division_id
   → join teams: team_name, captain_user_id, contact
   → join divisions: name as division_name, sort_order as division_sort_order
3. 위 결과에서 team_id 배열 추출
4. group_teams → groups (type = 'league')를 team_id 기준 조회
   → group_id, group_name, group_order, team_id 매핑
5. profiles를 captain_user_id 목록으로 조회
   → id, display_name 매핑
6. team_attendance에서 tournament_id = tournamentId, team_id IN [목록] 조회
   → attended 상태 맵 생성
7. 1~6 결과를 메모리에서 병합하여 AttendanceRow[] 반환
8. division_sort_order → group_order → team_name 순서로 정렬
9. 에러 발생 시 { data: null, error: message } 반환
```

> **쿼리 전략**: Supabase JS SDK의 `.from().select(...)` 체인으로 각 테이블을 개별 조회 후 메모리 병합.  
> 다중 FK JOIN을 하나의 체인으로 표현 시 SDK 한계로 타입 추론 오류가 발생할 수 있으므로 단계 분리 채택.

**`toggleTeamAttendance(tournamentId: string, teamId: string, attended: boolean): Promise<ActionResult>`**

의사코드:
```
1. createSupabaseServerClient() 호출
2. auth.getUser()로 현재 사용자 확인 (null이면 에러 반환)
3. team_attendance upsert:
   { tournament_id, team_id, attended, checked_by: userId, checked_at: now() }
   onConflict: (tournament_id, team_id) → UPDATE attended, checked_by, checked_at
4. 에러 시 { ok: false, error: message } 반환
5. 성공 시 { ok: true } 반환
```

#### 4-2. `app/(app)/admin/tournaments/[id]/attendance/AttendanceTable.tsx` (클라이언트 컴포넌트)

의사코드:
```
"use client"

Props: { teams: AttendanceRow[], tournamentId: string, isFinished: boolean }

상태:
  - localAttended: Record<team_id, boolean> // teams 배열로 초기화
  - pendingTeamId: string | null
  - errorMessages: Record<team_id, string>

KPI 계산 (useMemo):
  - total: teams.length
  - checked: Object.values(localAttended).filter(Boolean).length
  - unchecked: total - checked

handleToggle(teamId: string):
  1. pendingTeamId 설정
  2. optimistic: localAttended[teamId] 반전
  3. startTransition(async () => {
       result = await toggleAttendanceAction(tournamentId, teamId, !prevValue)
       if (!result.ok) {
         localAttended[teamId] = prevValue  // 롤백
         errorMessages[teamId] = result.error
         setTimeout(() => errorMessages[teamId] = "", 1500)
       }
       pendingTeamId = null
     })

렌더:
  섹션1: KPI 카드 3개 (전체/출석/미확인)
    - 미확인 > 0이면 미확인 숫자 text-rose-600
  섹션2: 헤더 줄 (제목 + Excel 내보내기 <a download> 버튼)
  섹션3: Table 컴포넌트
    - teams.length === 0이면 EmptyState (확정 팀 없음)
    - teams 행 렌더링:
        [디비전] [조 or "—"] [팀명] [주장이름 or "-"] [연락처]
        [체크박스] disabled=(isFinished || pendingTeamId===teamId)
    - 행 아래 에러 메시지 (errorMessages[teamId] 있을 때)
  섹션4: 결과 입력으로 이동 버튼 (오른쪽 정렬)

isFinished가 true이면:
  - 체크박스 전체 disabled
  - "대회가 종료된 이후에는 출석 기록을 수정할 수 없습니다." 안내 텍스트 표시
```

> 재사용 패턴:
> - `useTransition` 패턴: `app/(app)/admin/tournaments/[id]/result/components/ResultForm.tsx` 참고
> - KPI 카드 레이아웃: `app/(app)/admin/tournaments/[id]/page.tsx`의 readinessKpis 섹션 참고

### Phase 5. 대시보드 통합 (진행 상태 머신 + ProgressIndicator)

#### 5-1. `lib/api/tournamentProgress.ts`

**`TournamentProgressState` 타입 변경**

의사코드:
```
// 기존
type TournamentProgressState = "TEAM_APPROVAL" | "MATCH_GENERATION" | "SCHEDULE" | "RESULT" | "TOURNAMENT_FINISHED"

// 변경 후 ("ATTENDANCE_CHECK" 삽입)
type TournamentProgressState = "TEAM_APPROVAL" | "MATCH_GENERATION" | "SCHEDULE" | "ATTENDANCE_CHECK" | "RESULT" | "TOURNAMENT_FINISHED"
```

**`resolveState()` 함수 수정**

의사코드:
```
// 기존 마지막 두 줄:
if (summary.scheduledMatches < summary.totalMatches) return "SCHEDULE"
return "RESULT"  // ← 이 줄을 변경

// 변경 후:
if (summary.scheduledMatches < summary.totalMatches) return "SCHEDULE"
return "ATTENDANCE_CHECK"  // 스케줄 완료 후 출석 체크로 전환
// RESULT는 dashboard의 결과 버튼 또는 직접 URL로 접근
```

> **중요**: `RESULT` 상태는 제거하지 않음.  
> `resolveState()`가 `ATTENDANCE_CHECK`를 반환하더라도, 결과 입력은 URL 직접 접근 또는 출석 체크 페이지의 "결과 입력으로 이동" 버튼으로 가능하게 유지.

**`resolveNextAction()` 함수 수정**

의사코드:
```
// ATTENDANCE_CHECK 분기 추가 (SCHEDULE와 RESULT 분기 사이):
if (state === "ATTENDANCE_CHECK") {
  return {
    label: "출석 체크하기",
    url: `/admin/tournaments/${tournamentId}/attendance`,
    disabled: false,
    reason: null,
  }
}

// 기존 RESULT 분기는 그대로 유지 (직접 접근 시 사용됨)
```

**`buildSteps()` 함수 수정**

```
// 기존 스텝 배열 구성 순서:

// 3. 스케줄 (index 2)

// 5. 결과 (index 4)

// 출석 체크 스텝 조건:
attendanceDone = false  // 완료 조건 없음
attendanceActive = scheduledMatches === totalMatches && totalMatches > 0
attendanceStatus = attendanceActive ? "active" : "pending"

// 출석 체크 액션:
actions = [
  {
    label: "출석 체크",
    href: `/admin/tournaments/${tournamentId}/attendance`,
    enabled: !isFinished && scheduledMatches === totalMatches && totalMatches > 0,
    reason: isFinished ? "종료된 대회"
            : (totalMatches === 0 || scheduledMatches < totalMatches) ? "먼저 스케줄을 완료하세요"
            : undefined,
    variant: "primary",
  },
  {
    label: "결과 입력",
    href: `/admin/tournaments/${tournamentId}/result`,
    enabled: !isFinished && totalMatches > 0,
    reason: isFinished ? "종료된 대회" : totalMatches === 0 ? "경기가 없습니다" : undefined,
    variant: "secondary",
  },
]
```

## 5. 구현 순서 및 의존 관계

```
[1] package.json (xlsx 설치)
     ↓ xlsx가 없으면 API route 빌드 불가
[2] 0255_team_attendance.sql → Supabase 적용
     ↓ 테이블 없으면 API 코드가 런타임 에러
[3] lib/api/attendance.ts (타입 + 함수)
     ↓ AttendanceRow 타입 없으면 페이지/컴포넌트 작성 불가
[4] attendance/actions.ts
     ↓ 서버 액션 없으면 AttendanceTable에서 호출 불가
[5] app/api/.../export/route.ts
     ↓ (독립 가능, xlsx 설치 후 병행 가능)
[6] attendance/page.tsx
     ↓ getTeamsWithAttendance, getTournamentForEdit 필요
[7] attendance/AttendanceTable.tsx
     ↓ page.tsx에서 import
[8] lib/api/tournamentProgress.ts 수정
     ↓ (독립 가능, 페이지 완성 후 통합)
[9] admin/tournaments/[id]/page.tsx 수정 (buildSteps)
     ↓ tournamentProgress.ts 타입 변경 반영
[10] StepDescriptions.ts 수정
      ↓ (독립 가능, 마지막 작업)
```

**병행 가능한 작업**:
- `[4]` actions.ts 와 `[5]` export/route.ts는 `[3]` 완료 후 동시 진행 가능
- `[8]~[10]` 은 `[7]` 완료 후 독립적으로 진행 가능

## 6. 리스크 및 주의사항

### 6-1. Supabase SDK 다중 JOIN 한계

**문제**: `getTeamsWithAttendance()`에서 6개 테이블(applications, teams, divisions, group_teams, groups, profiles, team_attendance)을 한 번에 JOIN하면 SDK 타입 추론이 깨질 수 있음.

**대응**: 테이블을 3~4개 그룹으로 분리하여 개별 조회 후 TypeScript에서 Map으로 병합.
```
쿼리 1: tournament_team_applications + teams + divisions (핵심 목록)
쿼리 2: group_teams + groups (league type만, team_id 기준 Map)
쿼리 3: profiles (captain_user_id 목록 기준 Map)
쿼리 4: team_attendance (tournament_id 기준 Map)
→ 메모리에서 team_id 기준 병합
```
단, N+1 쿼리 없이 목록 기반 IN 조회로 쿼리 수는 4개로 고정.

---

### 6-2. group_teams 복수 그룹 배정 주의

**문제**: 한 팀이 league 그룹 + tournament 그룹 양쪽에 배정될 수 있음.  
league 그룹 필터 없이 JOIN하면 같은 팀이 중복 행으로 나타남.

**대응**:
```
group_teams 조회 시 groups.type = 'league' 필터 반드시 적용
LEFT JOIN이므로 group 없는 팀(경기 생성 전)은 group_id = null로 처리
```

---

### 6-3. `resolveState()` 변경에 따른 기존 동작 변경

**문제**: SCHEDULE 완료 상태에서 기존에는 `RESULT`를 반환했으나, 변경 후 `ATTENDANCE_CHECK`를 반환.  
대시보드 "다음 행동" 카드가 스케줄 완료 즉시 결과 입력 → 출석 체크로 바뀜.

**대응**:
- 대시보드 출석 체크 스텝 카드에 "결과 입력" secondary 버튼을 제공하여 직접 이동 가능하게 유지.
- `/admin/tournaments/[id]/result` URL 직접 접근은 인증 외 별도 제약 없이 항상 열려 있음.

---

### 6-4. `toggleTeamAttendance()` 동시성

**문제**: 두 운영자가 동시에 같은 팀의 출석을 토글하면 race condition 발생 가능.

**대응**:
- `team_attendance` upsert는 `(tournament_id, team_id)` PK 기반이므로 DB 레벨에서 중복 방지.
- `attended`는 마지막 쓰기가 유효 (Last Write Wins). 현장 운영 맥락에서 허용 가능.
- `AttendanceTable`의 `pendingTeamId` 상태로 클라이언트 중복 클릭은 방지.

---

### 6-5. ProgressIndicator 그리드 레이아웃 변경

**문제**: 5→6 스텝으로 증가 시 `lg:grid-cols-3`에서 2행 × 3열 = 6개로 맞아떨어지나,  
향후 스텝이 더 추가되면 레이아웃 재검토 필요.

**대응**: 이번 구현에서는 변경 없음. 향후 7번째 스텝 추가 시 레이아웃 재설계 필요.

---

### 6-6. Excel 다운로드 API route 인증

**문제**: Next.js App Router의 API route에서 Supabase 세션 쿠키 기반 인증을 사용하므로,  
`createSupabaseServerClient()`가 올바르게 동작하는지 확인 필요.

**대응**:
- `src/lib/supabase/server.ts`의 `createSupabaseServerClient()`가 `cookies()`를 사용하므로 API route에서도 동일하게 작동함.
- 기존 `app/(app)/admin/tournaments/[id]/applications/page.tsx` 패턴과 동일한 방식으로 인증 처리.

---

### 6-7. xlsx 패키지 설치 실패 대응

**문제**: `npm install xlsx` 실행 시 peer dependency 충돌로 에러가 발생할 수 있음 (기존 확인됨).

**대응**: `npm install xlsx --legacy-peer-deps` 로 재시도. 실패 시 `exceljs` 대안 패키지 검토.

## 7. 결론

총 **신규 파일 6개 + 수정 파일 4개**로 구현.  
Phase 순서 준수가 핵심: DB 마이그레이션 → 타입 → API → 프론트 → 대시보드 통합.

가장 주의할 구현 포인트:
1. `getTeamsWithAttendance()`의 다중 테이블 병합 로직 — 단계 분리 쿼리 + Map 병합 방식 채택
2. `resolveState()` 한 줄 수정이 전체 진행 플로우에 영향 — 결과 입력 우회 경로(직접 URL, secondary 버튼) 반드시 유지
3. `toggleTeamAttendance()` upsert — `onConflict` 옵션 명시 필수
