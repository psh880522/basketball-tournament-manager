## 1. 구현 범위 요약

### 1-1. 이번에 구현할 것

| 항목 | 구체 내용 |
|------|----------|
| Google OAuth 로그인/가입 | `supabase.auth.signInWithOAuth({ provider: "google" })` |
| Kakao OAuth 로그인/가입 | `supabase.auth.signInWithOAuth({ provider: "kakao" })` |
| OAuth 콜백 처리 강화 | `/app/auth/callback/route.ts` — 신규/기존 유저 분기, 역할 기반 리다이렉트 |
| OAuth 신규 유저 약관 동의 페이지 | `/terms` 신규 페이지 (`app/(auth)/terms/`) |
| 약관 동의 서버 액션 | `app/(auth)/terms/actions.ts` — `saveTermsConsentAction()` |
| 로그인 페이지 OAuth 버튼 통합 | `/login` — `OAuthButtons` + `OAuthDivider` 추가 |
| 회원가입 페이지 OAuth 버튼 통합 | `/signup` — `OAuthButtons` + `OAuthDivider` 추가, subtitle 변경 |
| OAuth URL 에러 파라미터 표시 | `/login` — `searchParams.error` 읽어 에러 박스 표시 |
| OAuthButtons 컴포넌트 | `components/auth/OAuthButtons.tsx` — Google / Kakao 버튼 |
| OAuthDivider 컴포넌트 | `components/auth/OAuthDivider.tsx` — "또는" 구분선 |

### 1-2. 제외할 것

| 항목 | 이유 |
|------|------|
| Apple 로그인 | 이번 범위 외 |
| 이메일/비밀번호 로그인 개편 | 기존 기능 유지 |
| 계정 연결/통합 기능 | 이번 범위 외 (동일 이메일 충돌 시 에러 메시지로 안내만) |
| 회원 탈퇴 자동화 | 이번 범위 외 |
| MFA (2차 인증) | 이번 범위 외 |

| DB 마이그레이션 | 기존 `handle_new_user()` 트리거로 OAuth 유저 자동 처리 가능. 스키마 변경 없음 |
| RLS 정책 변경 | 기존 `auth.uid()` 기반 정책이 OAuth 세션과 완전 호환 |
| ProfilePopup 이메일 null 처리 추가 | 기존 코드에 `email ?? "사용자"` 이미 적용됨 |

### UI spec [QUESTION] 결정 사항

| 질문 | 결정 |
|------|------|
| "나중에 동의하기" 링크 제공 여부 | **제거** — 필수 약관 동의 강제. 법적 안전성 우선 |

### Phase 2. 서버 액션 / API 레이어

#### 2-1. `app/auth/callback/route.ts` 수정

**핵심 변경:** 기존의 단순 `next` 파라미터 리다이렉트에서, OAuth 플로우와 이메일 플로우를 명확히 분기하는 로직으로 확장.

**분기 설계 (의사코드):**

```
GET /auth/callback?code=xxx[&next=...]

[1] errorCode 처리 (기존 로직 유지)
  → link_expired → /forgot-password?error=link_expired (reset flow)
  → link_expired → /login?error=link_expired (그 외)

[2] code 없음 처리 (기존 로직 유지)
  → /login?error=missing_code

[3] exchangeCodeForSession(code)
  supabase = createSupabaseServerClient() // 단일 클라이언트 인스턴스로 이후 모든 쿼리에 재사용
  const { error } = await supabase.auth.exchangeCodeForSession(code)
  if (error)
    → /login?error=oauth_provider_error (OAuth 에러)

[4] next 파라미터 유무로 이메일 플로우 vs OAuth 플로우 구분
  if (next !== null)
    → 기존 이메일 플로우: NextResponse.redirect(next)
    (이메일 확인 링크, 비밀번호 재설정 등 기존 동작 완전 보존)
    
[5] OAuth 플로우 처리 (next === null)
  a. 유저 정보 조회 (같은 supabase 인스턴스 재사용)
     const { data: { user } } = await supabase.auth.getUser()
     if (!user) → /login?error=session_error
  
  b. 신규 유저 판단
     isNewUser = (Date.now() - new Date(user.created_at).getTime()) < 10_000
  
  c. 약관 동의 여부 판단 (같은 supabase 인스턴스로 직접 쿼리)
     const { data: termsRows } = await supabase
       .from("user_terms_consents")
       .select("terms_type, agreed")
       .eq("user_id", user.id)
       .in("terms_type", ["service", "privacy"])
       .order("consented_at", { ascending: false })
     
     // 각 타입별 최신 행의 agreed 값 확인
     serviceAgreed = termsRows에서 service 최신 행의 agreed (없으면 false)
     privacyAgreed = termsRows에서 privacy 최신 행의 agreed (없으면 false)
     hasRequiredTerms = serviceAgreed && privacyAgreed
  
  d. 신규 유저 OR 약관 미동의 → 약관 동의 페이지
     if (isNewUser || !hasRequiredTerms)
       → /terms?next=/onboarding/completion?step=signup
  
  e. 기존 유저 & 약관 동의 완료 → profiles 테이블에서 role 조회 (같은 supabase 인스턴스)
     const { data: profile } = await supabase
       .from("profiles").select("role").eq("id", user.id).single()
     
     role = profile?.role
     if (role === "organizer" || role === "manager") → /admin
     if (role === "player") → /dashboard
     else (role === "user") → /onboarding/completion?step=signup
```

**재사용 패턴:**
- `createSupabaseServerClient()` — 기존 패턴 그대로
- `NextResponse.redirect()` — 기존 패턴 그대로

> **핵심 주의:** `exchangeCodeForSession()` 호출 후 세션 쿠키가 업데이트된다.  
> 이후 Supabase 쿼리는 **반드시 같은 `supabase` 인스턴스**를 재사용해야 세션이 올바르게 적용된다.  
> `getUserWithRole()`, `getMyTermsConsentStatus()` 등 내부적으로 새 클라이언트를 생성하는 함수는 콜백 라우트에서 사용하지 않는다.

#### 2-2. `app/(auth)/terms/actions.ts` 신규

```
"use server"

saveTermsConsentAction(input: { agreeService, agreePrivacy, agreeMarketing, next }): Promise<ActionResult>

1. agreeService, agreePrivacy 중 false → return { ok: false, error: "필수 약관에 동의해주세요." }

2. consentInputs 배열 조립 (기존 signUpWithPassword와 동일한 패턴)
   [
     { terms_type: "service",   terms_version: TERMS_VERSIONS.service,   agreed: true },
     { terms_type: "privacy",   terms_version: TERMS_VERSIONS.privacy,   agreed: true },
     { terms_type: "marketing", terms_version: TERMS_VERSIONS.marketing, agreed: agreeMarketing },
   ]

3. recordTermsConsentBatch(consentInputs) 호출
   if error → return { ok: false, error: "약관 동의 저장 중 오류가 발생했습니다." }

4. redirect(next) — next는 "/onboarding/completion?step=signup" 기본값
```

**재사용 패턴:**
- `recordTermsConsentBatch()` from `lib/api/terms.ts` — 기존 함수 그대로 사용
- `TERMS_VERSIONS` from `lib/constants/terms.ts` — 기존 상수 그대로
- `ActionResult` from `lib/types/api` — 동일 패턴

### Phase 5. 권한 정책 (RLS)

**변경 없음.** 모든 기존 RLS 정책이 `auth.uid()` 기반으로 OAuth 세션과 완전 호환.  
`user_terms_consents` 테이블의 기존 RLS 정책도 `user_id = auth.uid()` 기반이므로 변경 불필요.

## 6. 리스크 및 주의사항

### 6-1. 콜백 라우트 쿠키 동기화 문제 (★ 가장 중요)

**문제:** `exchangeCodeForSession()` 호출 후, 같은 요청 내에서 다른 함수를 통해 새 Supabase 클라이언트를 생성하면 세션이 올바르게 적용되지 않을 수 있다.

**이유:** `createSupabaseServerClient()`는 `React.cache()`로 래핑되어 있으며 `cookies()`를 내부에서 호출한다. Route Handler에서 `exchangeCodeForSession`이 `setAll` 콜백을 통해 응답 쿠키를 업데이트해도, 같은 요청에서 `cookies()`를 다시 읽으면 업데이트된 세션이 반영되지 않을 수 있다.

**해결:** `app/auth/callback/route.ts`에서 `createSupabaseServerClient()` 1회 호출 후, 그 인스턴스를 `exchangeCodeForSession`, `getUser`, `from("profiles")`, `from("user_terms_consents")` 모든 쿼리에 재사용한다. `getUserWithRole()`, `getMyTermsConsentStatus()` 등 내부에서 새 클라이언트를 생성하는 함수는 콜백 라우트에서 직접 호출하지 않는다.

### 6-2. 기존 이메일 플로우 보존

**문제:** `app/auth/callback/route.ts`에 신규 로직을 추가하면 기존 이메일 확인 링크, 비밀번호 재설정 링크 동작이 깨질 수 있다.

**해결:** `next` 파라미터 유무로 명확히 분기한다.
- `next` 있음 → 기존 로직 (`NextResponse.redirect(next)`) 유지
- `next` 없음 → OAuth 플로우 신규 로직 실행

기존 이메일 확인 redirectTo: `/auth/callback?next=/onboarding/completion?step=signup`  
기존 비밀번호 재설정 redirectTo: `/auth/callback?next=/reset-password`  
OAuth redirectTo (신규): `/auth/callback` (next 없음)

### 6-3. Kakao 이메일 null 처리

**문제:** Kakao OAuth로 가입한 사용자는 `auth.users.email`이 `null`일 수 있다.

**영향 파일 점검:**
- `app/(auth)/login/Form.tsx` — 에러 박스에 이메일 표시하지 않음 → 문제 없음
- `components/layout/ProfilePopup.tsx` — `email ?? "사용자"` 이미 처리 → 문제 없음
- `app/(auth)/terms/page.tsx` — 이메일 표시 없음 → 문제 없음
- `lib/api/terms.ts`의 `recordTermsConsentBatch` — `user.id` 기반, 이메일 무관 → 문제 없음

**결론:** 추가 처리 불필요.

### 6-4. 동일 이메일 계정 충돌

**문제:** 이메일/비밀번호로 이미 가입한 계정과 동일 이메일로 OAuth 로그인 시도 시 Supabase가 에러를 반환할 수 있다.

**현재 처리 방식:** `app/auth/callback/route.ts`에서 `exchangeCodeForSession` 실패 시 `/login?error=oauth_provider_error`로 리다이렉트한다. 이 케이스를 `email_conflict`로 세분화할 수도 있지만, Supabase 에러 메시지에서 이 케이스를 구분하는 것이 불안정할 수 있다. 우선 `oauth_provider_error` 메시지로 통합 처리하고, 추후 에러 메시지 파싱으로 세분화 가능.

### 6-5. 신규 유저 10초 판단의 경계 케이스

**문제:** 네트워크 지연 등으로 `created_at`과 현재 시각의 차이가 10초를 초과하면 신규 유저를 기존 유저로 오판할 수 있다.

**영향:** 신규 유저가 `/terms`가 아닌 역할 기반 경로로 이동. 이 경우 `user` role이므로 `/onboarding/completion?step=signup`으로 이동 (기존 `user` role 처리 로직에 의해). 이후 약관 미동의 상태이므로 서비스 일부 기능이 제한될 수 있으나, 다음 로그인 시 `hasRequiredTerms === false`로 다시 `/terms`로 이동.

**허용 가능한 수준의 엣지 케이스**로 판단. 필요시 10초 → 30초로 여유 늘릴 수 있음.

### 6-6. `Supabase Dashboard` 설정 선행 필요 (코드 외)

구현 시작 전 아래 설정이 완료되어야 한다:

1. Supabase Dashboard → Authentication → Providers → Google 활성화 + OAuth Client ID/Secret 입력
2. Supabase Dashboard → Authentication → Providers → Kakao 활성화 + REST API Key 입력
3. Supabase Dashboard → Authentication → URL Configuration → Redirect URLs에 추가:
   - `http://localhost:3000/auth/callback`
   - `https://<production-domain>/auth/callback`
   - Vercel Preview URL (`https://*.vercel.app/auth/callback`) — 와일드카드 지원 여부 확인
4. Google Cloud Console → OAuth 2.0 → Authorized redirect URIs에 Supabase 프로젝트 콜백 URL 추가
5. Kakao Developer Console → 앱 → 플랫폼 → Web → 사이트 도메인, Redirect URI 추가

### 6-7. `NEXT_PUBLIC_SITE_URL` 환경 변수 확인

`OAuthButtons.tsx`에서 `redirectTo` URL 조립 시 사용. 이미 `app/(auth)/signup/actions.ts`에서 동일하게 참조 중.
- `.env.local`: `NEXT_PUBLIC_SITE_URL=http://localhost:3000` 설정 여부 확인
- Vercel Dashboard: Production, Preview 각각 설정 여부 확인

### 6-8. `app/(auth)/terms/` 라우트 그룹 경로

Next.js App Router에서 `(auth)` 그룹은 URL에 포함되지 않는다.  
`app/(auth)/terms/page.tsx`의 실제 접근 URL은 `/terms`.  
`/auth/terms`가 아님에 주의. 콜백 라우트에서 `/terms?next=...`로 리다이렉트해야 한다.
