## 1. 구현 범위 요약

### 1-1. 이번에 구현할 것

| 항목 | 설명 |
|---|---|
| **[대회 상세 레이아웃 전면 재구성]** | 포스터+소개를 좌측에, 대회기본정보+선택형 디비전카드+CTA를 우측 sticky에 배치. Hero 섹션 제거. |
| **[디비전 선택 인터랙션]** | 우측 패널 디비전 카드 클릭 시 선택 하이라이트 + CTA 활성화 (데스크탑) |
| **[모바일 하단 고정 바 + 바텀시트]** | `MobileApplyBar` (md:hidden) + `DivisionBottomSheet` (기존 `BottomSheet` 래핑) |
| **[신청 URL에 divisionId 포함]** | CTA 링크: `/apply` → `/apply?division=xxx` |
| **[신청 페이지 — identity_verified_at 서버 체크]** | `apply/page.tsx`에서 `profiles.identity_verified_at IS NULL`이면 인증 페이지로 redirect |
| **[신청 페이지 — divisionId 수신 + division 드롭다운 제거]** | `?division=xxx` searchParam 필수. 없으면 대회 상세로 redirect. Form의 division 드롭다운 제거. |
| **[DivisionSummaryCard]** | 신청 페이지 상단, 선택된 디비전 읽기 전용 요약 카드 |
| **[최소 로스터 인원 강제]** | DB에 `min_roster_size` 컬럼 추가 + Form 클라이언트 비활성 + 서버 액션 검증 |
| **[RosterCounter]** | 선택된 인원 수 + 최소 인원 가이드 텍스트 실시간 표시 |
| **[신청 완료 배너]** | `my-applications/[id]?from=apply` 진입 시 `CompletionBanner` 표시 |
| **[입금 기한 카운트다운]** | `PaymentDueCountdown` — `payment_due_at`까지 남은 시간 실시간 표시 |
| **[router.push에 ?from=apply 추가]** | 신청 완료 후 상태 페이지에서 배너 표시를 위한 분기 신호 |
| **[rosterWarning 토스트 처리]** | 일부 선수 추가 실패 시 현재 무시하던 warning을 router.push 전 에러 메시지로 표시 |

### 1-2. 제외할 것

| 항목 | 이유 |
|---|---|
| 대회 탐색/목록 페이지 (`/tournaments`) | 이미 구현 완료 — 이번 범위 외 |
| 일정/대진/결과 확인 페이지 (`/tournament/[id]/result`) | 별도 플랜으로 분리 |
| Division별 자격 조건 (성별, 나이 등) | DB 컬럼 자체 없음 — 장기 과제 |
| 신청 완료 알림 발송 | `notifications` 시스템 미완성 — 별도 플랜 |
| 로스터 마감일 커스터마이징 (`roster_lock_at`) | DB 컬럼 없음 — 별도 과제 |
| `max_roster_size` 서버 검증 | DB에 컬럼만 추가. 검증 로직은 다음 플랜에서 처리 |
| 본인인증 페이지 자체 (`/onboarding/identity`) | 이미 존재 — redirect 연결만 |
| login 후 redirectTo 파라미터 처리 | 현재 login 페이지에 해당 로직 없으면 별도 구현 필요. 이번 플랜에서는 단순 redirect만 |

### Phase 1. DB 스키마 / 마이그레이션 [완료]

**파일**: `supabase/migrations/0251_divisions_roster_config.sql`

**핵심 로직 (의사코드)**:
```sql
-- divisions 테이블에 로스터 설정 컬럼 추가
ALTER TABLE divisions
  ADD COLUMN IF NOT EXISTS min_roster_size integer NOT NULL DEFAULT 5,
  ADD COLUMN IF NOT EXISTS max_roster_size integer;

-- 제약 조건
ALTER TABLE divisions
  ADD CONSTRAINT divisions_min_roster_size_check CHECK (min_roster_size >= 1),
  ADD CONSTRAINT divisions_max_roster_size_check CHECK (
    max_roster_size IS NULL OR max_roster_size >= min_roster_size
  );

COMMENT ON COLUMN divisions.min_roster_size IS '참가 신청 시 필수 최소 선수 수. 기본 5명.';
COMMENT ON COLUMN divisions.max_roster_size IS '로스터 최대 인원. NULL이면 제한 없음.';
```

**롤백**:
```sql
ALTER TABLE divisions
  DROP COLUMN IF EXISTS min_roster_size,
  DROP COLUMN IF EXISTS max_roster_size;
```

**주의**: `DEFAULT 5`이므로 마이그레이션 실행 즉시 기존 모든 divisions에 `min_roster_size = 5` 적용됨. 기존 신청 데이터에는 영향 없음.

  if (!dueAt) return
  const interval = setInterval(() => {
    setTimeLeft(computeTimeLeft(dueAt))
  }, 1000)
  return () => clearInterval(interval)
}, [dueAt])

// computeTimeLeft(dueAt):

//   elif diff < 6 * 3600 * 1000: return "HH:MM:SS 남음" (text-rose-600 font-bold)

## 6. 리스크 및 주의사항

### 6-1. `submit_tournament_application` RPC의 역할 검증 — captain vs manager

현재 RPC (`0233_applications_submit_rpc.sql`)는 `role_in_team = 'manager'` 를 확인한다. 실제 앱에서 captain이 신청하는 구조라면 `0237_fix_submit_rpc_captain_role.sql` 마이그레이션이 이를 수정했어야 한다. **구현 전 반드시 현재 RPC 정의 확인 필요.** 수정되어 있지 않으면 신청이 항상 실패함.

### 6-2. `DivisionRow` 타입 변경의 파급 범위

`DivisionRow`는 `admin` 영역에서도 사용한다. `min_roster_size`, `max_roster_size`를 추가해도 기존 SELECT에서 해당 컬럼을 포함하지 않는 쿼리는 `undefined`를 반환하므로 타입 오류가 발생할 수 있다. **admin 영역의 `getDivisionsByTournament` 호출부도 타입 체크 필요.** (실제 값은 DB DEFAULT로 채워지므로 런타임 오류는 없음 — 타입스크립트 컴파일 에러 주의)

해결 방법: `min_roster_size`를 `DivisionRow`에 optional (`min_roster_size?: number`)로 추가하거나, 모든 SELECT 문에 해당 컬럼을 포함.

### 6-3. `identity_verified_at` 체크와 redirect 루프

`getProfileVerification()` 호출 시 사용자가 `player` role이면 이미 인증 완료 상태여야 한다. 그러나 `identity_verified_at IS NULL`인 `player` 사용자가 존재할 수 있는 엣지 케이스에서 `/onboarding/identity?redirectTo=apply...` → 인증 완료 → redirectTo 로 돌아올 때 apply 페이지가 다시 체크해 통과해야 정상 동작. redirect 루프 여부는 onboarding identity 페이지의 완료 후 redirect 로직에 달려 있음. **사전 확인 필요.**

### 6-4. `TournamentStickyPanel` — 기존 CTA 분기 로직 누락 위험

기존 `page.tsx`의 우측 패널에는 6가지 분기가 있다:
- `open` + 미신청 → "팀 참가 신청"
- `canReapply` (cancelled/expired + open) → "다시 신청하기"
- `payment_pending/paid_pending_approval/waitlisted` → "신청 현황 보기"
- `confirmed` → "내 팀 보기"
- `draft` + organizer → "관리하기"
- `isResultVisible` → "결과 보기" 배너

`TournamentStickyPanel`로 이전 시 **이 6가지 분기 중 하나라도 빠뜨리면 안 됨.** 이전 전후 동작 비교 테스트 필수.

### 6-5. `applyWithRosterAction` 서버 검증 — Supabase RLS와 server action 인증

Server Action에서 `getDivisionById()`를 호출하면 `createSupabaseServerClient()`가 사용된다. 이 클라이언트는 요청 컨텍스트의 쿠키를 이용해 인증된 사용자 세션을 가져온다. `divisions` 테이블의 SELECT RLS 정책이 공개 허용인지 확인이 필요. 현재 앱에서 `getDivisionsByTournament()`가 미인증 상태에서도 동작하는 것을 볼 때 공개 SELECT일 가능성이 높으나, 운영 환경에서 다를 수 있으므로 **마이그레이션 이후 실제 Server Action에서 divisions SELECT가 정상 동작하는지 확인.**

### 6-6. 모바일 하단 바 z-index 충돌

`MobileApplyBar`는 `z-30`. 기존 헤더/네비게이션 바의 z-index와 충돌 여부 확인 필요. `BottomSheet`는 overlay `z-40` / sheet `z-50`이므로 MobileApplyBar는 그 아래. 기존 헤더의 z-index가 30 이상이면 충돌. **구현 전 기존 헤더 z-index 값 확인.**

### 6-7. `payment_due_at` 카운트다운의 SSR Hydration 불일치

`PaymentDueCountdown`은 `useEffect` + `setInterval`로 클라이언트에서 실행. 초기 SSR HTML과 클라이언트 hydration 간 시간 값이 다르면 React가 hydration warning을 발생시킬 수 있음. 해결: 초기 `timeLeft`를 `null`로 설정하고 첫 `useEffect` 실행 후에만 표시하거나, `suppressHydrationWarning`을 해당 요소에 사용.

### 6-8. `min_roster_size` DEFAULT 5 — 기존 운영 중인 대회

마이그레이션 직후 기존 `divisions`의 `min_roster_size`가 5로 설정됨. 이미 로스터 0~4명으로 신청 완료된 기존 신청들에는 **소급 적용 없음** — 검증은 신규 신청에만 적용되므로 기존 데이터 정합성 이슈 없음.
